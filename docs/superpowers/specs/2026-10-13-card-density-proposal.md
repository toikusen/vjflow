# 提案：擁擠段落的道具與卡片密度控制

日期：2026-10-13　狀態：提案，尚未實作　分支：feat/lyric-editing（B′ 驗收與提交之後才開始）

標示：**已驗證** = 讀程式碼或量測資料確認；**推論** = 從資料推得、未實測；**未測** = 還沒有資料。

## 1. 目前確認的擁擠片段（已驗證）

資料來源：v6 收尾報告（`version.uncommitted = d12a825613`，B′）的 `motion.json`，以及各首 run3／run4 的 treatment。

「退讓」是指 `avoid()` 在畫面上找不到空間時，把故事道具降到 55% 透明、留在歌詞後面（`graphics.ts` 的 fallback）。

| 歌 | 退讓次數 | 主要發生在 |
|---|---|---|
| チョロイン | 20 | 0–15 s、64–84 s、185–212 s（hero 旋轉木馬 + stack／scatter）；40–47 s、160–172 s（卡片堆） |
| 雙截棍 | 4 | 3 句 beat-cut（歌詞框就是全畫面）、c046 frame-split |
| Utsusemi | 1 | c005 stair |
| 其他三首 | 0 | — |

チョロイン的細節：

- **20 次退讓中，15 次當下沒有卡片**，在場的只有 hero（`horse.carousel`，x 0.75、y -0.55、size 0.36）。
- 卡片相關的只有 5 次：
  - c016：39.7–46.9 s 的對話泡泡卡堆，4 張
  - c061–c064：160.8–171.6 s 的便條卡堆，5 張，每 2.2 s 落下一張，最後一起清掉
- 退讓集中在 `stack`（13 次）和 `scatter`（3 次）：這兩種模板的字大、會佔掉多個位置。
- c003 一行 20 個字，被自動縮放到 0.89。

由此可見，這首歌擁擠的主因是**大字級的 stack 句子和貫穿全曲的 hero 搶位置**，卡片只是其中兩段。所以提案的範圍，從「卡片」擴大到「所有故事道具與裝飾圖層」，卡片是其中一類。

## 2. 現行機制與缺口（已驗證：讀程式碼）

1. **退讓是瞬間跳變。** `blendLayer` 在 0.4 s 內平滑過渡位置與大小，但透明度只有 `ui` 類圖層會漸變；hero、卡片從 100% 變成 55% 是同一幀內完成，這就是「突然閃現或消失」的來源。
2. **沒有優先順序。** `avoidAll` 依圖層順序逐一找位置；hero、卡片、裝飾照片一樣對待，先放的先佔位置。裝飾圖層（照片、色塊、印章）擠不出去時會留在原處、維持全不透明（只有 `ui` 類會變淡）。
3. **卡片堆不看空間。** `cards` 依 `every` 秒數固定落下，直到 `to` 才一起清掉，數量不因畫面擁擠而調整。
4. **量測缺口**：
   - 動態檢查只看 sprite／card，沒看裝飾圖層。
   - 隱藏中的 hero（透明度 0）也被算成畫面上的道具，例如 c016 在 46.34 s 時 hero 其實是隱藏的。
   - 報告沒有記錄是哪一個道具退讓。

## 3. 提案：本機編排的密度控制

全部在渲染端以確定性規則完成，不增加導演呼叫，也不加 API 重試。

**順序：先修量測（3.5），再評估密度策略。** 量測沒修好之前（隱藏中的 hero 被算成碰撞、可見的裝飾圖層沒算進去），新舊比較會失真。

### 3.1 辨識空間不足

渲染前的排版階段已經算出每句的避讓框（靜止框 + 動態餘裕）。新增一道「密度判斷」：

- **時間切段**：以歌詞框的出現與消失時間點切成時段，同一時段內的畫面組成固定。
- **算空位**：每個時段算出畫面扣掉歌詞框聯集後，還能放下多少道具（用現有 `avoid()` 的候選位置試放即可，不另寫一套幾何）。
- **判定擁擠**：該時段內，按優先順序（3.2）依序試放；放不下的道具，標記為「這個時段要讓位」。

判斷在建構時一次做完，結果寫進執行狀態，播放時只讀結果，同一份 treatment 每次結果相同。

### 3.2 優先順序

hero 不是固定的最高優先。它是チョロイン擁擠的主要來源，如果永遠優先保留，只會把其他元素擠掉，問題本身沒有解決。

取捨順序：

1. **歌詞可讀性**：永遠最優先，不為任何道具犧牲。
2. **當下重要的故事內容**：
   - 和正在唱的句子有關的卡片（例如「嘘つき！」對上 c062）。
   - hero 在它的重要段落：狀態變化（crack、shatter、gather、glow）的前後，以及導演讓它出場的段落開頭。
3. **其他元素逐一取捨**：hero 在一般段落、卡片堆裡和當下無關的卡片、pop／fly、裝飾圖層。依當下擁擠的程度，選擇縮小、換位、暫時淡出，或退讓成 55%。

hero 不必全曲都佔著位置：在歌詞密集的段落可以縮小、移位或暫時淡出，在重要段落再回來。

**hero 部分超出畫面**：允許，但依素材設定，不當成所有擁擠情況的預設解法。

- 純裝飾、背景型的 hero 可以裁切。
- 臉部、文字、標誌、關鍵辨識部位必須留在畫面內。
- 每個道具素材需要一個「可裁切的邊」或「必須保留的區域」標記；沒有標記的一律不裁切。標記放在道具素材的設定裡，不放進 treatment（推論：這樣不會改到 treatment schema；實際格式待定）。

### 3.3 卡片數量

- **同時可見的上限**：卡片堆同時可見的張數，取「這個時段放得下的張數」與原本張數的較小值，至少 1 張。
- **舊卡片先離場**：超出上限時，和當下無關的最舊卡片用原本的清除動畫（0.4 s 淡出）提早離場，不是消失。
- **重要卡片不刪**：和歌詞有關的卡片放不下時，依序嘗試延後出場、換位置、調整尺寸。不能因為預計顯示時間短就直接刪掉。
- **只有無關的卡片會因時間太短而不出場**：門檻先用 1.2 s 當實驗值。能不能讀完要看卡片文字長短，實驗時記錄每張卡片的字數與實際顯示秒數，再決定規則。
- **文字不刪**：卡片上的文字不刪除也不改寫，只調整出場時間、位置、尺寸。

### 3.4 不閃現、不突然消失

- **透明度也漸變**：讓位、退讓、回復都用 0.3–0.4 s 漸變。`blendLayer` 的透明度漸變擴大到故事道具，裝飾圖層也一樣。
- **只在句子交界改變**：一句歌詞顯示期間，道具不換讓位狀態（不在句中途跳）。
- **讓位有最短持續時間**：一個道具因擁擠讓位後，維持一段時間，避免一進一出。先用「段落結束或 2 s」當實驗值。
- **回來時不能卡位**：道具回到原位前要確認下一句的歌詞框；若會佔到下一段歌詞的位置，就延後回來，不能為了避免閃動而壓到字。
- **hero 讓位用離場動畫**：沿用既有的 hide 動畫（向下淡出），不用瞬間降透明度。

### 3.5 量測同步修正

- 動態檢查排除透明度 ≈ 0 的道具。
- 動態檢查加入裝飾圖層，另成一類記錄。
- `motion.json` 記錄是哪一個道具（hero／卡片第幾張／裝飾種類）、讓位原因與持續秒數。

## 4. 驗收方式

**先做小範圍原型。** 只選三種片段，用同一份 treatment 比較現行 B′ 和「B′ + 密度控制」，確認有改善、沒有誤刪重要內容，再擴大到六首：

- **hero 擁擠**：チョロイン 0–20 s、64–86 s
- **卡片堆擁擠**：チョロイン 158–175 s（便條卡堆 + stack）
- **原本不擁擠**：世界のつづき、行星 各取一段（v6 量測兩首都沒有道具退讓）。預期完全不變，用來確認規則不會誤傷。

**必須改善的具體案例**（來自 B′ 驗收時的影片抽查，2026-10-13）：

- **チョロイン c003**：長句被推到上方、縮小後，藍字疊在藍色舞台照片上，辨識明顯吃力。問題不只是字級，也包括背景對比。
- **チョロイン c061 附近**：兩張粉色半透明卡片互相重疊，文字彼此穿透，形成雜亂的背景。主歌詞大致可辨識，但「退成半透明」不能算是解決了視覺問題。

**原則：優先減少文字背後的視覺干擾，不再靠縮小歌詞來解決擁擠。**

原型通過後，再用下表對六首做完整比較。**不只看碰撞數字。**

| 項目 | 怎麼量 | 通過條件 |
|---|---|---|
| 歌詞可讀性 | `metrics.json` 的讀不完句數、每句完整可讀秒數 | 讀不完句數不增加；可讀秒數不減少 |
| 卡片保留 | 每張卡片實際顯示秒數、是否出場 | 列出每張卡片的變化；與當下歌詞有關的卡片要出場；沒有顯示不到 1.2 s 的卡片 |
| hero 存在感 | hero 可見時間（透明度 > 0.9 的秒數） | 列出變化，供觀感判斷 |
| 退讓 | 退讓次數與總秒數，依道具分列 | 列出變化（預期下降，但不是唯一標準） |
| 閃現 | 每個道具每秒透明度變化的最大值 | 沒有單幀內超過 0.2 的跳變 |
| 完整影片觀感 | 擁擠片段的並排影片 | 由你判斷閱讀舒適度、畫面是否變空、節奏是否自然 |

擁擠片段（觀感驗收用）：

- チョロイン：0–20 s、38–50 s、60–86 s、158–175 s、185–215 s
- 雙截棍：c046 附近（155–160 s）
- Utsusemi：c005 附近（34–39 s）

## 5. 範圍估計（推論；分兩步，先量測、後策略）

- 第一步（量測）：`engine.ts` 的 motionQa（排除隱藏道具、納入裝飾圖層、記錄道具身分）、`render.mts` 的報告欄位。
- 第二步（策略）修改：`engine.ts`（密度判斷、讓位狀態）、`story.ts`（卡片上限、hero 讓位）、`graphics.ts`（透明度漸變、優先順序）。
- 測試：`runtime.spec.ts` 或新的 spec，測純函式部分（時段切分、優先排序、最短持續時間）。
- 報告：`render.mts`（motion.json 欄位）。
- 共 4–6 個檔案，不改 treatment schema。若需要讓導演標記卡片優先順序，會動到 schema，屆時另提。

## 6. 風險與待決問題

- **畫面變空**：讓位太積極會讓畫面變空、失去敘事。只用規則判斷不保證好看，需要觀感驗收（推論）。
- **hero 部分超出畫面**：已決定允許，但依素材標記；素材標記的格式與誰來標（人工或規則）待定。
- **卡片與歌詞的關聯**：比對方式先用文字包含；誤判率未測。
- **裝飾圖層的影響**：裝飾圖層加入量測後，碰撞數字預期會增加。這是量測範圍變大，不代表畫面變差。
- **跨語言風格**：這個提案只處理密度，不處理六首風格收斂的問題（見風格對照文件）。
