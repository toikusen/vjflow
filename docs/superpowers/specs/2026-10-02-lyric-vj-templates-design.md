# 歌詞 VJ：模板庫＋AI 素材（A＋C）垂直切片設計

日期：2026-10-02（第 2 版：依審查意見修訂）
狀態：待審
分支：`feat/lyric-vj`（從 `feat/song-dna` 分出）

## 背景

- vjflow 的 cinematic spike 證明了「LLM 導演寫企劃 → 引擎逐格離線渲染」可行，但畫面仍是程式生成的場景，和資料庫裡設計師用 AE 做的歌詞 VJ 有距離。
- vjanalytics 已完成 50 支歌詞 VJ 的分析資料庫（4,462 個文字事件、段落、設計模式；文字與時間抽查約 96% 正確），以及「歌曲 → 2D 歌詞 VJ 影片」原型（無頭 Chrome 逐格擷取＋ffmpeg，已輸出 indigo 人聲版／伴奏版）。
- 決定：
  1. **A＋C**：設計過的動態模板庫（A）＋ AI 生成插畫與動態素材（C）。
  2. **離線輸出影片檔**，再帶到 Live House 播放；不要求即時。
  3. **沒有設計師**：品質來源改為資料庫真實作品當視覺目標、AI 審稿與審片、開發時逐幀調整。
  4. vjflow 是產品主體；vjanalytics 降為資料庫與分析後台（Python）。

## 目標

1. 一首歌、一種風格（偶像歌詞 VJ），做出可以和資料庫同類作品並排比較的影片。
2. 全自動：輸入音檔（＋可選的伴奏、歌詞、風格），輸出 1080p30 H.264 MP4（人聲版與伴奏版）。
3. 量測每首歌的成本與時間。

非目標：多風格、帳號付費、即時播放、模型訓練（LoRA）、人工編輯介面、筆順動畫。

| 彈跳 | 48 | 31% |
| 遮罩擦出 | 48 | 8% |

這只支持「先做哪些模板」。**「與參考作品的品質差距主要來自字體與版面」是推論**，由第 0 階段實驗驗證。

## 執行順序

| 階段 | 範圍 | 目的 |
|---|---|---|
| **0. 微型切片** | indigo 第一次副歌 15–20 秒；2 個模板（`punch`、`frame-split`）；1 張插畫；1 段 Veo 影片 | 打通完整管線：時間軸 → 企劃 → 素材 → 審查 → MP4 兩版音軌；驗證影片素材取格與動態品質 |
| 1. 切片 | 0:00–1:30；6 個模板 | 原訂範圍，跑完整審查流程 |
| 2. 泛用性 | i REVOLUTION 同範圍 | 確認不是只對 indigo 有效 |

每階段結束都依「驗收」一節判斷是否進下一階段。

## 1. 時間軸（程式擁有）

### 1.1 歌詞時間來源與優先序

| 優先 | 來源 | 可信度標記 |
|---|---|---|
| 1 | 使用者提供的 LRC（視為已驗證） | `verified` |
| 2 | LRCLIB 的 synced lyrics，**通過人聲軌檢查**才採用：每句開頭 0.4 秒內有人聲的比例 ≥ 85%，且全句平均位移 ≤ 0.3 秒（vjanalytics 的量測方式） | `verified` |
| 3 | Whisper 對齊（vjflow 現有） | 有足夠匹配的句子 `aligned`；被內插的句子 `interpolated` |

- 每個 cue 帶 `timingSource` 與 `confidence`。`interpolated` 的句子不使用踩拍類效果（只淡入淡出），並列入待人工確認清單。
- 歌詞原文只能來自上傳、LRCLIB 或網路搜尋（vjanalytics 已驗證的流程）；沒有歌詞才用 Whisper 辨識文字。

### 1.2 兩種音軌共用一條時間軸

- 時間軸以**人聲版（原曲）**為準。
- 伴奏版：使用者提供伴奏時，以 onset 交叉相關量測偏移（vjanalytics 在 indigo 量到伴奏早 46 ms），合成時以 `adelay` 補正；合成後在 3 個位置量測兩版的偏移 ≤ 15 ms 才算通過。
- 沒有伴奏時：後台用 Demucs 分離（vjanalytics 已有）；分離品質不保證，輸出時標示為「分離伴奏」。

### 1.3 拍點與段落

- 拍點、強拍、段落邊界來自 vjflow 的音訊分析；導演只能引用，不能修改。

## 2. 企劃 v3（導演擁有呈現方式）

段落（section）是音樂結構；鏡頭（shot）是畫面單位，一個段落含一到多個鏡頭；歌詞 cue 掛在鏡頭底下。

```ts
interface TreatmentV3 {
  concept: string;
  styleAnchor: { prompt: string; palette: Palette; fonts: FontPairing };   // 全曲共用
  assets: AssetSpec[];
  shots: Shot[];
  cues: CueStyle[];
}

interface AssetSpec {
  id: string;
  kind: 'image' | 'video';
  prompt: string;                 // 不得要求畫面中出現文字
  from?: string;                  // video：以哪一張 image 為第一格
  layering?: 'single' | 'depth';  // depth = 需要前景遮罩（見 3.2）
}

interface Shot {
  id: string;
  start: number; end: number;     // 程式驗證：邊界必須落在 cue 開頭或強拍 ±0.15 s
  template: TemplateId;
  params: Record<string, number | string | boolean>;  // 依模板的參數 schema 驗證
  asset?: string;                 // AssetSpec.id
  camera: 'static' | 'push' | 'pan' | 'parallax';
  transitionIn: 'cut' | 'flash' | 'wipe' | 'dissolve';
}

interface CueStyle {
  cueId: string;                  // 對應時間軸的 cue；文字與時間不在這裡
  shot: string;
  rows?: number[];                // 換行位置（字元 index）；未給則依片語空格自動換行
  emphasis?: { from: number; to: number; method: 'scale' | 'color' | 'glow' | 'shake' }[];  // 字元範圍 [from, to)
  accents?: number[];             // 要踩的拍（相對於 cue 開始後第幾拍）
  enter: EnterKind; exit: ExitKind;
  variant?: string;               // 模板內的版面變體
}
```

**程式負責的驗證與修正**

- 未列出的 cue 用模板預設樣式；未知的 `cueId`、範圍越界的 `emphasis`、超出參數範圍的 `params` 會被拒絕並回饋給導演（最多重試 2 次），仍失敗就套預設值並記錄。
- 鏡頭必須無縫覆蓋整段範圍；不合規的邊界吸附到最近的 cue 開頭或強拍。
- **溢位**：渲染前量測文字。超出安全區時先縮小到模板的最小字級，仍超出就依片語空格重新換行，再不行就拆成兩個時段輪流顯示；每次自動修正都記錄成待審項目。

## 3. 模板（A）與素材（C）

### 3.1 模板

模板 = 版面＋字體排印＋圖形元件＋動態配方＋參數 schema（型別、範圍、預設值）。

| ID | 名稱 | 內容 | 階段 |
|---|---|---|---|
| `punch` | 關鍵字衝擊 | 關鍵字滿版放大、在 `accents` 拍點彈跳；其餘字小字環繞；拍點閃光 | 0 |
| `frame-split` | 框線分割 | 細線框＋角括號先畫出再進字；主句置中、副句在框外小字 | 0 |
| `outline-stack` | 描邊疊字 | 實心字＋描邊殘影錯位重複、斜排；殘影依拍延遲 | 1 |
| `brush-reveal` | 筆刷擦出 | 手寫字型＋**方向性筆刷遮罩**（沿排字方向擦出、筆刷紋理邊緣）；紙紋或網格底。不做筆順 | 1 |
| `side-vertical` | 插畫＋側邊直排 | 插畫框居中，歌詞直排在兩側框線內 | 1 |
| `depth-plate` | 插畫景深 | 前景／背景兩層，文字夾在中間，2.5D 視差；分層失敗退回單層視差（見 3.2） | 1 |

共用後製：bloom、色差、底片顆粒、光線掃過、拍點白閃；離線可做動態模糊（多次取樣平均）。字型只用可商用的開源字型，實作前逐一確認授權。

### 3.2 素材

- **生成模型**：插畫 Gemini 3.1 Flash Image 2K；動態 Veo 3.1 Fast 1080p，以插畫為第一格、8 秒；Veo 的聲音丟棄。
- **`depth` 分層**：不分別生成主體和背景（兩者不會對齊）。對同一張插畫做前景分割取得 alpha 遮罩，背景用圖像編輯把主體移除後補畫；兩者尺寸、位置天生一致。品質檢查：前景面積佔 5%–60%、邊緣不破碎。不通過就退回**單層視差**（整張圖推移＋景深模糊）。分割模型在實作時選定並記錄。
- **影片取格**：Veo 影片先用 ffmpeg 解成渲染幀率的圖片序列，渲染第 n 格時直接載入對應圖片，不依賴 `<video>` 的 seek。
- **鏡頭比 8 秒長**：程式把影片鏡頭切到 ≤ 8 秒；導演若給更長的鏡頭，後段改用同一張插畫的單層視差接續，接縫處以 0.5 秒交叉淡化。不使用倒放。

### 3.3 素材生命週期

```text
審稿通過的企劃
 → 生成風格錨點（第一張插畫）→ 看圖審查（必要時重生，最多 2 次）
 → 以錨點為參考批次生成其餘插畫 → 再生成影片
 → 關鍵畫面＋動態審查
```

- 審查的修改**預設只動模板參數與 cue 樣式**。只有審查明確判定「素材不可用」並寫出理由時，才重生該素材。
- 上限：每個素材最多重生 2 次；每首歌素材費用上限 US$10（可設定），超過就停止重生並列入待人工確認。
- 快取：以「模型＋prompt＋參考圖」的雜湊作為鍵，企劃沒有改到的素材一律沿用。

## 4. 渲染與輸出

- **方式**：Node 腳本用 Playwright 開啟渲染頁，逐格呼叫 `await renderAt(t)`（**非同步**：等待該格所需的貼圖、影片幀與字型都就緒才回傳），擷取畫面送給 ffmpeg 編碼。這是 vjanalytics 原型已驗證的做法。
- **移植範圍**：從 `spike/cinematic` 移植 Three.js 渲染骨架與 `treatment` 型別；`offline-render.ts`（WebCodecs）不移植，因為它在不支援 H.264 編碼時會改輸出 WebM，而且逐格回呼是同步的。
- **輸出**：1080p30 H.264 MP4 兩版（人聲、伴奏），同一份畫面。
- **執行環境**：Node 22+、Google Chrome（Playwright 以 `channel: 'chrome'` 啟動）、ffmpeg（含 libx264）。
- **資源**：平行渲染數依記憶體設定。vjanalytics 曾因 6 個平行渲染導致記憶體換頁吃滿磁碟，預設 2，並在可用空間不足時停止。

## 5. 審查與驗收

### 5.1 評分標準（審稿、審片、人工驗收共用）

1. 段落與鏡頭邊界落在歌詞句首或明顯的能量變化上；副歌從副歌第一句開始。
2. 副歌的畫面家族一致，而且逐次加強；最後一次副歌最強烈。
3. 畫面對應歌詞的意象和情緒，不是隨便挑的。
4. 相鄰鏡頭有足夠對比，整首有起伏。
5. 歌詞清楚可讀，不被亮處吃掉，也不被主體擋住。
6. 構圖：主體在三分線附近、地平線位置合理、畫面沒有過曝或全黑。
7. 每一幕都有設計過的版面，而不是「字放在中央」。
8. 素材風格全曲一致（畫風、配色）。
9. 對照資料庫參考畫面，質感不明顯落後。

### 5.2 三層審查

| 層 | 檢查什麼 | 方式 |
|---|---|---|
| 自動量測 | 可讀時間、踩拍精度、轉場位置、溢位、音軌偏移 | 渲染器回報每個 cue「完全可讀」（不透明度 ≥ 0.9 且動畫已穩定）的時間，須 ≥ min(1.0 秒, cue 長度 × 0.6)；每個 accent 與拍點誤差 ≤ 1 格；鏡頭邊界與企劃一致；兩版音軌偏移 ≤ 15 ms |
| AI 看圖審片 | 構圖、可讀性、風格一致、和參考作品比較（標準 3–9） | 每個鏡頭 2 張關鍵畫面，加上每個轉場與重點進退場各一條**幀序列**（約 0.6 秒內抽 8 格拼成一張圖）；同時附上資料庫參考畫面。最多修改 2 輪 |
| 人工 | 動態與整體感受 | 你看完整輸出（階段 0 為 15–20 秒、階段 1 為 90 秒） |

AI 審片看不到真正的動態，所以踩拍、可讀時間這類項目以自動量測為準，整體動態以人工為準。

### 5.3 通過條件

- 自動量測全部通過。
- 人工驗收：把成品和 3 支同類參考作品（例如 sweet timer、Mirrors、パステルシャイン）、vjanalytics 原型並排，你依標準 1–9 各打 1–5 分。**平均 ≥ 3.5、沒有任何一項 ≤ 2，而且你判斷「可以拿去 Live House 放」**，才算通過。這是主觀標準，所以同時保留每輪的分數與評語。

### 5.4 決策點

- 通過 → 進下一階段。
- 模板不錯但素材不一致 → 加強風格錨點或換生成模型，重做該階段的素材部分。
- 仍明顯落後（平均 < 3）→ 重新評估：外包少量模板設計，或改走 AE 模板自動化。

## 7. 架構

- **渲染**：vjflow 內新增渲染頁與模板 layer（Three.js）；Node 腳本負責逐格擷取與 ffmpeg。
- **後台工作**（素材生成、Claude 呼叫、資料庫檢索、Demucs）：先用 Node／Python 腳本，確認方向後再決定是否做後端服務。
- **資料庫**：從 vjanalytics 匯出 JSON 給導演使用；參考畫面從原片依事件時間抽格。

## 風險

- **AI 素材風格飄移**：風格錨點＋審片；仍飄就減少生成數量，同一張圖用不同運鏡重複使用。
- **文字被素材吃掉**：模板內建文字底板或遮暗區；自動量測加上標準 5。
- **沒有設計師的品質上限**：用參考畫面逐幀比對調整；決策點保留外包選項。
- **授權**：參考畫面只在內部審查使用，不進入輸出；生成素材的使用條款與 SynthID 浮水印需在對外販售前確認；字型逐一確認授權。
- **Veo 等待時間**：最長數分鐘，素材生成要平行並快取。
- **前景分割品質**：不穩定就退回單層視差，不阻擋整體流程。
