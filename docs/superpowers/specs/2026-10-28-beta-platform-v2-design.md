# 封測平台第二版：概念確認、成品區、回報與導演經驗庫

日期：2026-10-28　狀態：已核准（2026-10-28）　分支：feat/lyric-editing
前一版：`2026-10-27-closed-beta-platform.md`

標示：**已驗證** = 讀程式或實測確認；**推論** = 未實測；**重述版本** = 我對使用者意思的轉述，待確認；**我的決定** = 使用者沒指定、由我先定，可推翻。

## 1. 為什麼做

使用者（管理者本人試用「行星」後）提出：

- 現在一按「製作」就整個交給導演，使用者事前不能表達想要的感覺，事後也沒有地方說哪裡不好。
- 成品夾在三種方案卡片裡，看不出花了多久、花了多少錢。
- 平台要像 Kling、Tripo 那樣靠扣點數製作，所以每一次花費都要事先確認、事後看得到。
- 最重要的長期目標：**所有使用者回饋都要記下來，當成之後每首歌的經驗，讓導演越來越專業、越懂使用者要什麼**。但不好的意見、只適合某首歌的做法不能直接變成全體規則，要經過規劃判斷。

成功的樣子：使用者在花大錢之前看過並接受概念；做完能清楚看到成品、時間、費用；有問題能說清楚並選修正或重做；管理者能從後台看到每首歌每一步發生什麼事；回饋累積成經過篩選、導演真的會讀的規則。

## 2. 目標、非目標、反目標

目標
1. 製作分兩段：先出概念 → 使用者確認 → 才做完整影片。
2. 製作前可以填想要的概念（例：宮崎駿、日本動漫）、上傳參考資料、選風格或交給導演。
3. 版面重排：選方案 → 製作進度 → 成品區（獨立區塊，含花費時間、花費費用）。
4. 每個成品可回報：沒問題／有問題、哪裡（時間點＋類別）、說明、建議，並選「修正」「重做」或「只回報」。
5. 回饋全部原樣保存；整理成候選規則，經管理者審核後進入導演讀的經驗庫。
6. 後台有每首歌完整的製作紀錄：每一步的開始時間、耗時、費用、log、導演的選擇、自動檢查結果、回饋、管理者動作。
7. 間奏不硬放圖：沒人唱的地方預設只做背景變換與圖形動態，適合的歌才放圖。

非目標
- 金流、公開註冊、真正的點數幣別（仍以美元顯示，之後再換算點數）。
- 雲端移植、多台機器同時製作。
- 讓使用者逐鏡頭編輯畫面。

反目標（做到了也算失敗）
- 風格選單讓使用者選到不適合這首歌的風格，成品變差。（參考既有原則：裝置與風格只在歌曲適合時用。）
- 一位使用者的個人喜好或某首歌的特例，沒經審核就變成所有歌的規則。
- 沒有確認就扣錢；或使用者要等管理者才能往下走。
- 名字式的概念（宮崎駿、某部動畫）被做成模仿特定作品、角色或商標的畫面。

## 3. 現況（已驗證）

- 製作流程（`scripts/lyric-vj/beta/make.sh`）：無圖版 `direct` → `typeplan` → `horizon` → `render`；插圖版 `direct` → `props` → `typeplan --sprites` → `horizon` → `render`；故事版 `direct` → `typeplan`（與無圖版共用 `make/noimg`）→ `keyframes` → `cutout` → `horizon` → `render`。中間沒有停下來等使用者的點。
- 所有製作共用歌曲的 `make/` 資料夾，成品固定寫到 `video-<tier>.mp4`；歌詞時間在製作後還能改。同一方案做第二次會讀到上次的快取或覆寫舊片（make.sh:10、:54）。
- 導演只從 `PROVEN_LANGUAGES` 挑設計語言：目前 5 種（絲網海報、孔版印刷、網點檔案、諜報片頭、圖形卡），全部 46 種。`direct.mts --language <id>` 可指定。
- 風格下拉選單只在內部 `/studio` 頁（預設「交給導演依歌曲決定」，選項是全部語言）。封測頁從來沒有。
- 「填想要的概念」「上傳參考資料」：封測與 studio 頁面都沒有入口。但故事版的 `keyframes.mts` 已支援 `--style`（使用者指定畫風，並會把畫家、動畫工作室、作品名字改寫成視覺特徵、不出現名字）與 `--style-ref`（參考圖），keyframes.mts:132、:168。也就是能力已有一部分，只是沒接到介面，且只有故事版有。
- 經驗紀錄有兩處，且互不相通：
  - `out/design-lessons.md`：studio 的「依意見修改」直接附加原文；只有 `codelayer.mts` 讀。
  - `out/knowledge/lessons.md`：`lessons.mts` 用 Claude 把審片回饋整理成通則；只有 `keyframes.mts`、`cutout.mts`（故事版）讀。
  - **無圖版、插圖版用的 `direct.mts`、`typeplan.mts` 不讀任何經驗紀錄。**
- 間奏：故事版 `keyframes.mts` 明確要求「沒有歌詞的時段也要有畫面推進，一格最多停 9 秒」（keyframes.mts:161）。`typeplan.mts` 的提示已規定「前奏、間奏、尾奏不出現看得清楚的詞，用圖形、人物和節奏撐」、「間奏可以不鋪 backdrop」，但沒有規定不放道具圖片；插圖版的道具由 typeplan 依 `--sprites` 擺放。
- 費用：`##COST` 多半在一步成功後才回報，有些取 log 最後一個金額（make.sh:14–15）；中途失敗或中斷可能已花錢卻沒記到。收到第一筆實際成本後，額度就改用累積成本、不再用預留額，沒有執行中的上限（store.mts:45）。管理者重跑會建新工作，舊成本照算。
- 工作紀錄：`out/beta/db.json`（帳號、歌曲、工作），工作有 `startedAt`／`endedAt`／`phase`／`costUsd`（`##COST` 累加）；工作的標準輸出存 `out/beta/logs/<job>.log`；各步驟的詳細 log 在 `songs/<id>/make/*.log`。**每個階段的開始時間沒有記錄**（只有目前階段）。
- 實測：「行星」準備 16.5 分鐘、$0.011；插圖版 23.4 分鐘、$3.62（預留 $6），其中導演一步約 9 分鐘、$2.02。
- 營運限制：一台 Mac、一次一個工作；server 重啟會把「執行中」的工作改回排隊並從頭跑（各步驟會跳過已有輸出）；`make.sh` 執行中不能原地改寫（bash 邊跑邊讀）；`ng build` 會先清空 `dist/`，server 正在提供這個資料夾。

## 4. 設計

### 4.1 製作兩段：概念 → 確認 → 製作

流程（每首歌、每個方案）：

1. 使用者在「製作新版本」區選方案，選填概念文字、參考資料、風格，按「產生概念」。確認視窗顯示預留金額（概念階段）。
2. 系統只跑導演那一步，產出概念卡。
3. 概念卡內容：設計語言名稱、配色色票、字型、主題物件、故事大綱（依段落，一段一兩句）、間奏打算怎麼處理、對使用者概念的回應（「你寫的『宮崎駿』我理解成：手繪水彩、田園光線、溫暖⋯⋯」）、2–3 張示意畫面。
4. 使用者三選一：
   - **接受，開始製作**：確認視窗顯示剩餘步驟的預留金額 → 跑完整流程。
   - **依意見調整**：填一句話，導演以這版為基礎改（重跑導演一步，有費用）。
   - **換一個方向**：導演重想（重跑導演一步，有費用）。
5. 概念卡在使用者回應前一直保留，不佔用機器（工作狀態「等你確認概念」，佇列可以先做別人的）。

我的決定：
- 接受的概念是承諾，不只是參考：設計語言、配色、字型、主題物件、段落故事、間奏處理在後續步驟必須維持。現在 `typeplan` 會替換圖層、改材質（typeplan.mts:371），故事版另外生成分鏡（keyframes.mts:152），所以要把概念當成後續步驟的輸入約束，並在交片前檢查一致性（例如配色、語言、字型與概念卡相同）。
- 示意畫面用現有 treatment 直接渲染幾個時間點的靜態畫面（不另外畫圖）；插圖版、故事版此時還沒有道具或角色，示意畫面只代表文字、配色與背景。若 builder 判斷渲染單張成本太高，可先只給色票＋大綱。
- 預留拆兩段：概念階段一筆、接受後剩餘步驟一筆。金額依實測訂（導演約 $2，見 §3），builder 依 `RESERVE` 結構調整。
- 「依意見調整」「換一個方向」每首每方案上限 3 次，避免無限燒錢（數字可調）。

### 4.2 製作前的輸入：概念、參考資料、風格

- **概念文字**（選填，500 字內）：例如「宮崎駿」「日本動漫」「90 年代港片」。導演必須先把它轉成可設計的特徵（媒材、光線、配色、線條、節奏、氛圍），寫在概念卡上給使用者看；不畫特定作品的角色、場景或商標。
- **參考資料**（選填）：圖片最多 5 張（jpg／png／webp，每張 10 MB 內）。導演看圖，同樣轉成特徵。網址不收（避免伺服器去抓外部內容）。
- **風格**（使用者決定 2026-10-28）：預設「交給導演」，另外列出所有設計語言（目前 46 種）。
  - 使用者看到的選單**不分**「已驗證」「實驗」，每種一樣是名稱、一句「適合什麼歌」、3–4 張參考圖。驗證狀態只在後台顯示。
  - 參考圖是選單的一部分，不是附件：沒有參考圖的風格不上選單。
  - 參考圖來源：
    - 已驗證的 5 種：用使用者驗收過的成品畫面（`scripts/lyric-vj/references/kits/<id>.jpg` 已有 8 格）。
    - 其他 41 種：現有的 `references/samples/<id>.jpg` 是 2026-10-11 測試的 5 格小條，舊渲染器、部分被使用者評為單調或沒有該風格的感覺，**不直接用**。改用目前的流程，拿評測歌單裡 1–2 首合適的歌各做一次概念＋示意畫面，管理者在後台挑可以上架的畫面；管理者沒挑過的風格不上選單。
  - 推論：有了概念確認，選到不穩定的風格時，使用者在看到示意畫面後就能放棄，只損失概念那一筆；所以不需要在前台警告。代價是未驗證風格的「調整概念」「重做」次數可能較多，後台要按風格統計接受率，接受率持續偏低的風格由管理者下架。
  - 導演自己挑（使用者選「交給導演」）時（使用者同意 2026-10-28）：不另外從頭驗證，改用三級，只在後台顯示：
    - **已驗證**：導演自由選（目前 5 種）。
    - **候選**：管理者為它挑過上架參考圖的風格（挑圖就是入門檢查）。導演可以選，但要在概念卡寫出「為什麼這首比已驗證的更適合」；示意畫面先過自動畫面檢查（現有審片評分），沒過就自動改用已驗證風格重做概念，費用由平台吸收，使用者只看到正常的概念卡；同一個候選風格升級前同時只出現在少數幾首歌（數字可調），避免導演為求新鮮一直挑新的。
    - **未上架**：沒有參考圖，導演不能選，使用者選單也沒有。
    - 升級與下架：後台按風格累計概念接受率、成品「沒問題」比例、「風格不對」回報數；達門檻（例如 3 首概念被接受、成品無「風格不對」，可調）出現在升級清單，管理者一鍵升為已驗證；接受率持續偏低的退回未上架。
    - 在 41 種的參考圖做好之前（§6 第 8 步），沒有任何候選風格，導演仍只選已驗證的 5 種、選單也只會出現這 5 種；機制先做好，參考圖晚點補。
  - 指定風格與歌曲、概念文字或參考圖衝突時（使用者決定 2026-10-28）：使用者優先。導演照使用者選的做，但在概念卡最上方寫清楚顧慮（例如「這首是慢歌，這個風格的節奏感很強，可能會顯得太躁」），使用者看完要再按一次確認才繼續。
- 概念文字與參考圖要接到所有方案：導演（direct）、文字動態（typeplan）都要收；故事版沿用 keyframes 既有的 `--style`／`--style-ref`，不重做。
- 這三項都存進該次製作的紀錄，也存進經驗庫的原始資料（使用者想要什麼本身就是經驗）。

### 4.3 間奏不硬放圖

- 規則（適用所有歌、所有方案）：沒有人唱的段落（前奏、間奏、尾奏，依時間軸上沒有歌詞的區間判斷）預設**不放道具或插圖**，靠背景換段、圖形動態、節奏撐畫面。
- 例外由導演判斷並寫出理由：例如這首歌的故事在間奏有關鍵事件，或間奏很長、單靠背景會空太久。理由要寫在 treatment 上，讓概念卡和後台看得到。
- 落點：導演（`direct.mts`）決定每段間奏的處理並寫進 treatment；同一份決定傳給 `typeplan.mts`（插圖版擺道具）與故事版的 `keyframes.mts`（現在要求間奏一定要有畫面推進，keyframes.mts:161，要改成依這份決定），最後在交片前檢查（道具出現在無歌詞區間且沒有例外理由 → 修掉）。只改 typeplan 的話，故事版會在下游把圖加回來。
- 驗證：用固定的評測歌單（benchmark）跑前後對照，確認間奏不會變成空白、也沒有其他段落退步。

### 4.4 版面

歌曲列表（`/my`）：每首歌一張精簡卡（封面字、歌名、狀態、最新成品縮圖），點進去是歌曲頁。

歌曲頁（`/my/song?id=`，我的決定：從列表頁拆出來，因為一首歌會有多個版本與回報，全塞在列表會太擠）由上到下：

1. **歌曲資訊**：歌名、歌手、語言、歌詞時間狀態（「再看一次歌詞時間」連結）。
2. **製作新版本**：三種方案改成可選的卡片（選一張會亮起），下面是概念文字、參考圖、風格選單，最下方一顆「產生概念・預留 $X」。有工作在跑時這區停用並說明原因。
3. **進行中**：目前的工作。概念階段顯示進度；概念出來後顯示概念卡與三個按鈕；製作階段顯示現有的步驟進度（百分比、剩餘時間、步驟清單）。
4. **成品**：每個完成的影片一張卡，新的在上：
   - 影片播放器、下載 1080p。
   - 方案、設計語言、完成時間、**花費時間**（工作開始到結束，概念＋製作分開列）、**花費費用**（實際扣的金額，概念＋製作分開列）。
   - 使用者當初填的概念與參考圖（縮圖）。
   - 「回報這個作品」按鈕；已回報的顯示回報摘要與處理狀態。
   - 由「修正」產生的新版本標示「依回報修正自 v1」。

### 4.5 問題回報

表單（成品卡展開）：

- 整體：**沒問題**／**有問題**。選沒問題就只要一鍵送出（可加一句話）。
- 有問題時可加多筆「哪裡」：在播放器上按「標記目前時間」記下時間點（可拖成區間），每筆選類別（歌詞看不清、時間不準、圖片不搭、畫面空、風格不對、節奏轉場、其他）並寫說明。
- 建議：自由文字。
- 處理方式三選一：
  - **修正**：保留現在的設計，只改回報的問題（費用較低）。
  - **重做**：從概念重新開始（回到 4.1）。
  - **只回報，不用處理**。
- 送出前確認視窗顯示預留金額（修正、重做才有）。

「修正」怎麼做：`typeplan` 每次都會重建整首的圖層與歌詞配置（typeplan.mts:370、:404），所以不能保證「只改回報的地方」。第一版只開放修改範圍確定的修正類型，其他類別在表單上只提供「重做」或「只回報」：
- 第一版可修正（推論，builder 依程式確認）：間奏放圖（依時間區間拿掉道具）、某句歌詞看不清（該句的顏色或位置）、時間不準（回到歌詞時間頁改完重新渲染，不重跑導演）。
- 做法：沿用該次製作的 treatment 與道具，只套用針對性的修改再渲染；修完的是新版本，舊版保留。
- 之後再擴充可修正的類型時，每種都要有「修改範圍確定」的做法才開放。

使用者確認（2026-10-28）：「行星」的回報＝間奏不放圖片、只要背景變換，處理方式選「修正」，這次不實際重跑。使用者判斷「行星」這首就是間奏不該放圖；其他歌仍依是否適合決定。這筆要當第一筆原始回饋存進經驗庫。

### 4.6 導演經驗庫

三層，由原始到規則：

1. **原始回饋**（全部保留、不刪）：每筆回報、每次概念調整意見、使用者填的概念與參考圖、接受或換方向的選擇。附上當時的歌、方案、設計語言、版本、時間點。
2. **候選規則**：定期（例如每累積 N 筆，或管理者按一下）由 Claude 把原始回饋整理成候選規則，每條標：
   - 適用範圍：所有歌／某種設計語言／某種歌（例：慢歌）／只這首歌。
   - 依據：哪幾筆回饋、幾首歌、幾位使用者。
   - 和既有規則的關係：新規則、補強、衝突。
3. **已採用規則**：管理者在後台逐條採用、改寫或否決。採用的進入導演讀的經驗庫；否決的保留紀錄與理由（避免一再被提出）。

接線：`direct.mts`、`typeplan.mts`、`props.mts` 都要讀已採用規則（現在都沒讀），依適用範圍只餵相關的條目。
舊資料遷移：既有的 `out/design-lessons.md` 與 `out/knowledge/lessons.md` 全部匯入成「待審候選」，不是直接當已採用規則。舊的 `lessons.mts` 會把回饋直接泛化、衝突時以最新的覆蓋（lessons.mts:63、:73），而故事版要求遵守它（cutout.mts:407）；所以所有既有的讀寫端（studio 依意見修改、lessons.mts、keyframes、cutout、codelayer）都要一起改接審核後的結果，不能留後門繞過審核。

我的決定：不做全自動採用。理由是使用者明確要求「需要規劃考慮」，而且單一回饋最容易是個人喜好或特例。

### 4.7 後台製作紀錄

管理頁新增「歌曲」分頁，每首歌一條時間線：

- 每個工作：每一步的開始時間、耗時、費用（`##COST` 依步驟記，而不只是總和）、結束狀態、該步驟的 log（可展開、可下載）。
- 導演的選擇：設計語言、配色、字型、主題物件、故事大綱、修正清單（`director.json` 的 fixes）、間奏例外理由。
- 自動檢查：歌詞被遮比例、黑畫面、key shot 結果。
- 使用者輸入與回饋：概念文字、參考圖、概念調整意見、回報內容與處理方式。
- 管理者動作：重跑、放行、調額度。

費用紀錄：每一筆成本記成可去重的事件（哪一步、哪一次呼叫、金額、來源），分「已知」和「尚未結算」（一步中途失敗時，已呼叫但沒回報的部分要標出來）。成品卡顯示的花費用已知成本，有未結算時標示。
資料：每首歌一個只會往後加的事件檔（`songs/<id>/events.jsonl`），佇列在階段切換時寫入；`db.json` 的工作加上每步的時間與費用。這些時間也拿來校正進度條的預估分鐘數（現在是估計值）。

### 4.8 每次製作獨立（多版本的前提）

每次製作（概念、接受後的製作、修正、重做）建立一筆「製作」紀錄，存當時的輸入快照（song.json 與歌詞時間、方案、概念文字、參考圖、風格、回報內容）和自己的輸出資料夾（例如 `songs/<id>/runs/<run>/`），成品是 `runs/<run>/video.mp4`。不再共用 `make/` 與 `video-<tier>.mp4`。修正版從上一個製作的輸出複製或引用需要沿用的部分。

### 4.9 計費（使用者同意 2026-10-28）

- 每個方案固定價格，實際成本超出的部分由平台吸收；不會中途要求補錢。
- 價格分兩段：產生概念一筆、接受後剩餘一筆；只做到概念就放棄只收概念那筆。
- 調整概念、修正、重做各有固定價（修正最低）。
- 系統原因的失敗與重跑不扣使用者額度；使用者主動要求的調整、修正、重做才扣。
- 保險絲：單一工作實際成本超過該次訂價 2 倍時自動停止、通知管理者；使用者不需處理、不多扣。
- 價格依實測成本加餘裕訂，數字由 builder 依 §3 的實測與後台統計提出，管理者決定。
- 對應現況要改的地方：`charged()` 現在以實際成本取代預留（store.mts:45），要改成以固定價計使用者額度，實際成本另記成平台成本。

## 5. 限制

- 一台 Mac、一次一個工作；等使用者確認概念時不能佔住佇列。
- `make.sh` 要拆成可分段執行（概念段、製作段），各段的輸出檔沿用「已存在就跳過」，讓重啟可續跑。
- 部署：前端 build 到別的資料夾再同步到 `dist/`；不在有工作執行時重啟 server，除非接受該工作重跑。
- 參考圖與概念文字是使用者輸入：大小、格式、數量都要在 server 端驗證；只有擁有者與管理者看得到。
- 費用：每一次會花錢的動作（產生概念、調整、接受製作、修正、重做）都先確認、先預留。
